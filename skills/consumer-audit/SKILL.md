# 完成声明、消融与伪实现清理

## 0. 这份技能解决什么

防止三类交付失败：**声称完成但没有证据链**、**机制存在但没有消费者**、**改动了却证明不了改动有效**。
它给的是判据和格式，不是安慰。任何一节用不上时，如实说明用不上。

---

## 1. 边界声明：任何结论都必须带的三段

写完一个结论、一个数字、一个"可行"之前，先补三段：

- 观测范围。我在什么上测的（语料、平台、版本、样本数）。
- 已知边界。它不能被推广到哪里。写不出边界，说明还没想清测的是什么。
- 证伪条件。什么观测会推翻它。写不出证伪条件的，只能算印象。

禁止的词：应该、大概、一般来说、理论上可以。要么给判据，要么写"未验证"。

---

## 2. 任务完成声明：证据链格式

**"完成 / 已实现 / 已修复 / 已生效" 是结论，不是过程描述。** 用之前必须同时给全五栏：

```
判据：  <可反驳的判据：什么观测算通过，什么算不通过>
执行：  <实际跑过的命令 / 读过的路径>
观测：  <真实输出。不许写预期输出，不许转述>
归类：  applied_verified | coverage_gap | activation_gap
        | action_application_gap | consumer_verification_gap
边界：  <这次验证没有覆盖什么>
```

**缺任一栏，只能说"未验证"。**

五类缺口用词（来自 ACCF effectiveness-gap 分类法）：

| 归类 | 含义 |
|---|---|
| `coverage_gap` | 机制根本不覆盖这个情形 |
| `activation_gap` | 覆盖了，但从没被触发 |
| `action_application_gap` | 触发了，动作没被应用 |
| `consumer_verification_gap` | 应用了，但没人验证消费者真的观察到 |
| `applied_verified` | 落地了，且被观察到落地 |

**硬区分：外壳存在 ≠ 效果已验证。** 判断一个能力是否真有效，必须回答三问：
1. 谁消费它？
2. 产生什么**可观察**效果？
3. 什么情况会证伪？

注册了却无人调用的服务或工具 = 死代码，不算能力。

---

## 3. 消融实验

任何机制改动都要能回答：**去掉它，可观察结果会不会变？**

三条纪律：

1. **消融 ≠ 把输入弄坏。** 关掉数据源导致所有东西都变成缺陷，那是坏输入，不证明任何事。
2. **消融必须报告"证据买到了什么"**：with / without 两轮的 finding 差集，以及去重后真正新增了什么。
3. **必须写证伪条件**，并说明这个消融**不能**证明什么。

> 作者本人踩过的反例：把消费者计数关掉后，所有工具都被判成"从未调用"。那看起来差异巨大，实际只是把输入置空了。正确做法是让"关掉"变成**未评估**，而不是变成 0。

---

## 4. 第一性原理自审

对一个要交付的能力，按顺序回答：

1. 它的**最小可观察效果**是什么？
2. 谁消费它？消费者凭什么知道它生效了？
3. 它依赖哪些假设？逐条问"如果这条不成立会怎样"。
4. 有没有更便宜的等价方案？**在等价方案里选更优的，而不是选被允许的。**

禁止把"注册了 / 文件存在了 / 测试绿了 / JSON 能解析"当作"效果达成"。

---

## 5. 审查自身已有架构、skill 与插件

用 `consumer_audit` 工具（`action: "report"`）。它测量：composition 里声明了哪些行、每行装了哪个包、那个包注册了什么能力、那些能力在本机会话日志里被调用过几次。

读法：

| 报告里的项 | 含义 | 该怎么办 |
|---|---|---|
| `tool_never_invoked` | 注册了，日志里 0 次调用 | 死能力候选，去问"谁该消费它" |
| `tool_never_delivered` | 被调用过，但每一次返回都带 isError | 调用了却什么都没送到，比从不调用更值得看 |
| `skill_never_delivered` | 同上，针对 skill | 加载请求发了，skill 正文没送到 |
| `skill_never_loaded` | SKILL.md 在盘上，但 skill 工具从未以它的名字被调用过 | 看 detail：被列进目录多少次、加载过多少次，两者是不同的事实 |
| `prompt_only_capability` | 只有 prompt section，没有工具/服务/路由 | 说明书，不是机制 |
| `row_without_capability` | 行挂着，包在，但没有任何注册或 effect 站点 | 挂了个空壳 |
| `duplicate_prompt_section` | 两个包注册同名段 | 第二份真相，必须去重 |
| `package_unresolved` | 非第一方包解析不到 | 真问题；先确认搜索根是否覆盖到 |
| `intercepts_host_behaviour` | 包裹既有服务方法，不注册新能力 | 不是缺陷；调用计数判断不了它 |
| `skill_outside_searched_roots` | 被列进目录，但没有任何被搜索的根里有它的 SKILL.md | 项目级/用户级 skill 根不在扫描范围内 |

报告还有一节 `consumed`，逐条给出 `attempts` / `failed` / `succeeded`。finding 回答"是不是死的"，`consumed` 回答"用了几次、成了几次"。

**三层必须分开**：注册了（声明）→ 被调用过（有调用记录）→ 送达了（配对的返回不带 isError）。报告只走到第三层。
| `first_party_shipped` | 随 harness 一起发行 | **不是缺陷** |

**判据：服务必须有消费者。** 报告只测量，不做质量判断；一条 `tool_never_invoked` 不等于插件写得差，它只说明这条能力目前没有可观察的消费者。

### 5.1 内容有没有按设计生效，由你判断，不由工具判断

这句话是分工，不是免责。插件负责把记录交出来，判断由做这件事的模型下。

会话日志是多帧 zstd，模型没法用普通读取打开它。所以插件提供入口：

```
consumer_audit  action="evidence"  name="<工具或 skill 名>"  limit=5
```

它返回该能力最近若干次调用的**参数**和**返回正文**，以及每次的 `isError`。拿到之后按这个顺序做：

1. **读它本该做什么。** 打开该插件或 skill 的源码与正文，写下它设计的目标行为。
2. **读它实际做了什么。** 看参数是不是它被设计来接收的，看返回正文是不是它被设计来产出的。
3. **对齐或不对齐，都要给依据。** 指出是哪一次调用、哪个字段、哪一段输出支持你的判断。
4. **写下这次判断的边界。** 你看的是被扫描的那些日志；没看到的会话里它可能表现不同。
5. **不确定就说不确定。** 参数对但输出被截断、或输出看起来对但缺少下游结果，都要如实讲。

**禁止的反向操作**：不要因为"它被调用过"就说它生效了，也不要因为"输出看起来像那么回事"就跳过第 1 步。

复核纪律：报告给出的每一条都要能被**独立重数**推翻。别信工具的自述，去看日志。

---

## 6. 清理冗余与伪实现

按顺序做，不要跳：

1. **列去重候选**：同名 prompt section、同职责工具、同一份规则的两处副本、被取代但仍保留的旧机制。
2. **对每个候选问一句**：删掉它，谁会注意到？答不上来 → 删。
3. **更新时必须清理过期内容。** 只加不删的更新等于持续污染；"说了清理却每次保留"是已被明确抱怨过的行为。
4. **最小改动**：能复制粘贴复用的不重写，能局部改的不整文件重写，只写必须改写的。
5. **删除前留证据定位，删除后留回滚方式。**

---

## 7. 报告与状态纪律

- 每条断言绑定**证据定位**：`文件:行` / 命令 / 会话 `seq`。禁止无出处的断言。
- 状态用显式词：`applied` / `repair_required` / `stopped`。**`stopped` 不等于成功。**
- 结论先行；不确定就写"未验证"，不粉饰。

---

## 8. 反模式清单（实测踩过，勿重演）

- 把控制台编码问题当成产品缺陷。（先换一条解码路径复验，再下结论。）
- 字段名查错就下结论。（先 dump 出对象真实键名。）
- 负向对照里放了语料中真实存在的词。（对照词必须先用独立搜索确认不存在。）
- 把答案键放进被测语料目录。（题目泄漏，会污染全部结果。）
- 关掉数据源当成消融。（见 §3。）
- 材料出现在工具输出里却没形成联想历史关联。（"看到了"不等于"用上了"。）
- 用提示词冒充机制。闸门必须落在**产物、状态或可测测量**上。
